# Proposed virtual rule groups

These are retained **original first-class group proposal records**. Each has an independent closed analysis at `processing/specimens/groups/`; reviewed published versions live under `groups/`. No fifth task pipeline exists.

A group has its own stable ID, metadata labels, parent/child relationships, color identity, and member specimen references. Members are independently queued atomic rule specimens in `../SPEC-0013.json` through `../SPEC-0066.json`.

- **GROUP-0001** is the umbrella collection, with seven child groups and 54 deduplicated indirect members.
- **GROUP-0002** — Git & Repository Hygiene; 10 proposed members (`SPEC-0013` to `SPEC-0022`)
- **GROUP-0003** — Rust Quality; 10 proposed members (`SPEC-0023` to `SPEC-0032`)
- **GROUP-0004** — CI/CD; 8 proposed members (`SPEC-0033` to `SPEC-0040`)
- **GROUP-0005** — Documentation; 8 proposed members (`SPEC-0041` to `SPEC-0048`)
- **GROUP-0006** — Safety & Data Integrity; 5 proposed members (`SPEC-0049` to `SPEC-0053`)
- **GROUP-0007** — Releases; 7 proposed members (`SPEC-0054` to `SPEC-0060`)
- **GROUP-0008** — QA & Verification; 6 proposed members (`SPEC-0061` to `SPEC-0066`)

Group membership does not alter a member rule's normative effect, status, version, scope or authority. An opt-in "Add all" should resolve and add approved rule IDs only, with visible conflict/permission analysis. A group color derives from its own ID using the existing OKLCH hue generator, while retaining a readable text label.

The proposed ontology extension is tracked separately in `../SPEC-0067.json`. Until that specimen is processed and the resulting downstream work is independently authorized, these are reviewable intake records rather than published group objects.

The actual published group schema and website composer use canonical rule IDs rather than these original specimen IDs. Historical proposed membership is preserved solely for traceability. Nothing in this queue activates a published group.
